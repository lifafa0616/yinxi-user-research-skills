# 用户研究工作流 · Handoff 文档

> 本文档供下一个接手的人（或 AI 实例）快速理解项目背景、架构决策、当前状态和待办事项。
> **Source of truth 是本公开仓库 `~/Documents/yinxi-user-research-skills/Skill/yinxi-user-research/` 中的 Skill 文件。** 以后只在该目录改规则并推送公开仓库。`~/.factory/skills/` 是安装入口，目前仍为独立文件夹；待用户同意后改为指向该工作目录的符号链接。本文档只记录决策与状态，不复制规则原文。

## 1. 项目背景

### 起源

一份 21K 字的飞书用研教学工作流文档，描述了从业务目标到设计方向的完整用户研究流程。原始文档面向教师，内容详尽但学生直接使用时面临一个核心痛点：**面对 AI 输出不知"什么留什么不留"**。

### 目标

将这份教学工作流重构为两个 Factory Skill，让学生能独立跑完一条完整的用户研究流程（做研究 → 输出用户画像 → 输出设计方向），同时**理解每一步在做什么、为什么必须在这时候做**。

### 核心矛盾

Skill 提供便捷，但"一键输出"会让学生跳过理解。设计原则是**有界选择而非无界编辑**：闸门处给学生选项让他选，而不是让他在 AI 的长篇输出上自由编辑 —— 前者学到东西，后者学不到。

## 2. 架构决策

### 双 Skill 架构

| Skill | 角色 | 位置 |
|-|-|-|
| `yinxi-user-research-loop` | 主流程，控制 S1-S7 + 3 个闸门 | 安装入口：`~/.factory/skills/yinxi-user-research-loop/` · 唯一工作目录：`~/Documents/yinxi-user-research-skills/Skill/yinxi-user-research/yinxi-user-research-loop/` |
| `yinxi-user-research-interview` | 被访者，在独立对话中扮演用户 | 安装入口：`~/.factory/skills/yinxi-user-research-interview/` · 唯一工作目录：`~/Documents/yinxi-user-research-skills/Skill/yinxi-user-research/yinxi-user-research-interview/` |

**为什么分两个 skill**：防自证。如果同一个对话里既做研究又扮演用户，模型会复述自己的假设，访谈变成自证。独立对话让被访者只拿到中性代号 + 背景 + 场景，看不到任何行为 / 动机 / 痛点假设，也看不到 Persona 名称。

**两个 skill 之间的物理断点（重要）**：独立对话之间不共享上下文，主会话**看不到**访谈内容。因此流程里必须有显式的一步：学生把每份访谈记录**粘回主会话**。这份记录是 S3 校准、闸门② 定选、报告附件三处的同一份来源，少一份就断链。

### 流程结构（7 步 + 3 闸门 + 1 回传）

```
S1 候选 Persona（2-3 类）
  → 闸门① 访谈深度（可逆，各候选深度由学生自选，可点选卡片）
→ S2 访谈方案（含给学生的提问清单 + 每候选一份不含题目的《访谈身份交接包》）
  → 每个候选各开一个独立对话跑访谈
  → 学生把每份访谈记录粘回主会话   ← 不可省
  → 准入检查
→ S3 校准（模拟路径称"内部一致性校准"）
  → 闸门② 主 Persona 定选（模拟路径定出的是"待验证的主 Persona 假设"）
→ S3 续 核心任务流程地图
→ S4 需求
→ S5 功能与 KANO
→ S6 设计方向
  → 闸门③ 人决策自检
→ S7 自动生成报告（10 页左右）+《访谈记录文档》附件
```

### 关键参数

| 参数 | 值 | 理由 |
|-|-|-|
| Persona 类别数 | 2-3 类，最多 3 类（含多角色分类） | 超过 3 类时每类的访谈摊薄到 1 份以下，任何一类都拿不到能校准的输入 |
| 行为轴 | 2-3 条 | 轴超过 3 条会交叉出多于 3 个聚集点，与 3 类上限冲突 |
| 每类受访者 | 1 位 / 1 个独立对话 | 每类都要跑到，共 2-3 份记录 |
| 问题清单 | 6 道共同核心题（各候选逐字相同）+ 每候选 4-9 道专属题 | 核心题保比较基准，专属题保问题设计的针对性（问题设计本身是用研核心能力） |
| 访谈深度 | 由学生在闸门① 为每个候选自选 | 业务目标直接相关的一侧通常问全套；约束型或暂不深入的一侧可只问 6 道核心题。问得少有风险（漏掉未问部分的痛点），问得多有代价（每轮多 20-30 轮对话） |
| 追问 | 学生自行判断，不是规则 | 追不追问是学生根据当场回答质量的即时判断，skill 不强制、不计分 |
| 编号 | 候选代号-序号（A-01、B-03），不加行号 | 前缀让报告读者一眼看出证据来自哪一类；编号本身已唯一 |
| 闸门② 比较方式 | 只比 6 道共同核心题的逐项结果（支持 / 反驳 / 未覆盖） | 比条数偏向问得多的候选；命中率（命中 ÷ 题数）也不成立，因为各题覆盖面不同 |
| 报告页数 | 10 页左右，浮动一两页 | 重点两章因原话证据多而略超是合理的，不靠删证据压页数 |

### 16 条硬约束（速查，原文见 SKILL.md）

1. 缺业务目标或产品阶段时不生成，只追问
2. Persona 2-3 类，最多 3 类（含多角色分类）
3. S1 不定主 Persona（S3 闸门② 才定；模拟路径定出的是待验证假设）
4. 目标层级按业务目标填写（end 必写 / experience 默认写 / life 按需），保留矛盾
5. 每个 Persona 内容量以一页 PPT 为上限（≤350 字）
6. 分群前必须先输出分群依据；分群轴由业务目标导出（五类维度），人口属性须声明用途，不能单独成轴
7. S1-S3 不得输出设计启示 / 产品机会 / 功能建议
8. 两个重点交付物：最终版画像 + 设计方向
9. 每条结论标来源（事实 / 模拟回答 / 推断 / 常识）
10. 需求池只写"要解决的问题"，出现功能名即违规
11. 顺序不可颠倒：需求 → 功能 → KANO → 方向
12. 需求收口 3-5 条，功能 5-8 个，不做清单 ≥1（可来自 KANO 判定、超出范围、证据不足、暂缓验证，不得硬判）
13. 《访谈身份交接包》只含中性代号 + 背景 + 场景 + 逐题访谈说明，不给题目或题数，也不给行为 / 动机 / 痛点 / 期待、Persona 名称与分类标签；完整问题清单只交给学生逐题使用
14. 三个闸门必须停下等人
15. 证据模式选定后贯穿到底
16. Persona 输出前在后台按《Persona 质量条例》检查

### 教学机制

- **三段式进度条**：每回合开头显示当前在哪一段、还差几步
- **两行自曝**：每次输出结束前自报最弱判断 + 影响链
- **闸门可点选卡片**：三个闸门优先用交互式选择工具做成可点选选项（Factory 的 AskUser、Codex / Workbuddy 的等价卡片），不可用时退回编号文本。每个闸门 2-4 个选项，每项写清"选它意味着什么"，并留"我自己写"的出口

### 证据模式的性质区分（第二轮审查后确立）

模拟访谈的回答**不是用户事实**，它是另一层模型推演。因此两条路的措辞严格分开：

| | 模拟 | 真实 |
|-|-|-|
| S3 这一步叫 | 内部一致性校准 | 校准 |
| 闸门② 定出 | 待验证的主 Persona 假设 | 主 Persona |
| 引用称谓 | 模拟回答（标「模拟 A-07」） | 用户原话（标「A-07」） |

模拟路径的价值是暴露假设里的空洞与矛盾、训练提问与筛选，不是验证。

## 5. 关键决策记录

| 决策 | 阶段 | 理由 |
|-|-|-|
| 删除快跑模式 | 早期 | AI 自问自答没有对抗性，补规则也堵不住（判断权在同一模型手里） |
| Persona 最多 3 类 | 中期 | 超过 3 类时每类的访谈摊薄到 1 份以下，拿不到能校准的输入 |
| 深度选择交还学生 | 中期 | skill 只给建议和风险告知，选择权在学生 |
| 追问不是规则 | 中期 | 追问是学生根据当场交互的即时判断，不是流程节点 |
| 报告 10 页放宽 | 中期 | 原话证据占篇幅，重点两章略超合理 |
| 记录靠学生粘回主会话 | 第二轮审查 | 独立对话之间不共享上下文，这是唯一可靠的回传路径；主会话最终必须持有记录用于反向验证与报告附件 |
| 模拟 ≠ 验证 | 第二轮审查 | 模拟回答是模型推演，只能检验假设自洽性；措辞混用会让学生把推演当事实 |
| 交接包由主 skill 生成 | 第二轮审查 | 学生只需复制粘贴，降低操作成本，同时保证留空字段不被好心补全 |
| 问题清单拆两层 | 第二轮审查 | 问题设计本身是用研核心能力，要按业务目标与用户特性设计；但比较需要不变的基准，所以核心题逐字固定 |
| 闸门改可点选卡片 | 第二轮审查 | 有界选择才有教学价值；Factory / Codex / Workbuddy 三个环境都支持交互式选择 |
| 命中率降级 | 第二轮审查 | 各题覆盖面不同，命中率不是公平指标，会把提问量差异伪装成用户差异 |
